# Issue駆動開発フロー

## 1. 目的

この文書は、開発の起点をローカル VSCode 上での Claude Code 利用から GitHub 上に移し、GitHub Issue を起点として要件定義・設計・実装を進める今後の開発フローを整理するための資料である。

もう一つの目的として、このフローは「AI のみで開発を進められるか」を検証する場でもある。現時点では Claude Code と Codex の 2 つを組み込むが、これは最終形ではなく出発点である。将来的には他の AI（別ベンダーのコーディングエージェント等）も組み込み、複数の AI が互いに相談・レビューしながら開発を進められる体制を目指す。そのため本資料のフロー・命名規則・役割分担は、参加する AI の種類や数が増えても破綻しない形を意識して設計する。

本資料は **開発フロー**（Issue 起票 〜 dev フェーズ PR 承認 〜 OpenSpec アーカイブ）のみを対象とする。それ以降の、次バージョンの想定・`release/v<version>` 作成・バージョン更新・GitHub Release 作成・タグ付け・安定ブランチ（main）へのマージといった **リリースフロー** は、引き続き [ブランチ・リリース戦略](ブランチ・リリース戦略.md) を正とする。両者を1つの「全体フロー」に詰め込むと肥大化するため、本資料では明確に切り分ける。

## 2. 前提

- 個人利用前提のプロジェクトであり、過度に複雑な運用は避ける（[ブランチ・リリース戦略](ブランチ・リリース戦略.md) と同様の方針）
- 既存の `openwiki/`（現状仕様の自動生成ドキュメント）と `openspec/`（変更提案・仕様差分の管理）の枠組みをそのまま活用する
- 開発フローは **spec フェーズ**（提案）と **dev フェーズ**（実装）の 2 段階に明確に分離する（§3）。それぞれ専用ブランチ（`spec/<Issue番号>` / `dev/<Issue番号>`）を持ち、各フェーズの終わりに人間が確認する PR を置く。フェーズの切り替えをコメントコマンド（`@claude` 等の呼び分け）に頼らず、ブランチ構造そのもので表現することで、「どのトリガーを使えばよいか」が曖昧にならないようにする
- `dev/<Issue番号>` は `spec/<Issue番号>` から分岐する（`main` から取り直さない）。これにより spec フェーズで作成した OpenSpec 提案が dev フェーズにそのまま引き継がれる
- ブランチ運用・リリース手順は本資料では変更しない。`release/v<version>` 以降は引き続き [ブランチ・リリース戦略](ブランチ・リリース戦略.md) に従う
- 各フェーズの一次作成者を固定する: **spec フェーズは Claude Code が一次作成**、**dev フェーズは Codex が一次実装**を担当する。これはフェーズごとに異なる AI に主体性を持たせ、後続の AI 会議（レビュー）でも単一 AI の視点に偏らないようにするための役割分担であり、AI 会議（4.4 系）への参加自体は spec/dev 問わず Claude Code・Codex・qwen(Aider) の 3 系統で行う
- AI レビュー（提案・実装いずれも）は、個々の AI が独立にレビューして終わりではなく、その時点で使える全ての AI に議論させることを前提とする。現時点では Claude Code・Codex・qwen(Aider) の 3 系統だが、参加 AI が増えてもこの「全員で議論する」という進め方自体は変えない
- AI レビューの進行は「**指摘の収集は同時（並列）**、**指摘を踏まえたファイル編集の適用は引き続き 1 体ずつ順番**」という方式を取る。3 体が同一ブランチへ同時に書き込むと編集がコンフリクトするため、編集自体は逐次適用のまま、各 AI が指摘を出す工程だけ並列化する（将来 A2A 化する場合もこの前提を踏襲する）
- AI レビュー（提案・実装いずれも）は 1 回の議論で終わらせず、参加する全 AI が合意するまで「提示 → 議論 → 修正 → 再提示」を**最大 3 ラウンド**までループする。3 ラウンドで合意に至らなくても無限ループはさせず、その時点の内容のまま次のステップ（人間によるレビュー）へ進み、未合意である旨を明記する（既存 `issue-propose.yml` の実装と同じ上限値）
- ユーザーが開発フロー中に直接手を動かすのは、各フェーズ末尾の PR レビュー（spec フェーズ: 提案内容の確認、dev フェーズ: ビルド済み成果物の動作検証）のみとする。ソースコードそのもののレビューはユーザーの作業範囲に含めない。それ以外（提案作成、AI レビュー、実装、コードレビュー、ビルド）は AI 主導で進める
- dev フェーズの動作検証（5.5 相当）はユーザー本人にしかできない直列のボトルネックである。複数 Issue の spec/dev フェーズが並行して進んでいても、動作検証は 1 件ずつ順番に処理する
- dev フェーズのビルド確認は `feature/*` 相当（`dev/*`）への毎コミットで重いビルドが走らないよう、専用の `build/<name>` ブランチへの push をトリガーに行う。`build/<name>` の詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) を参照

## 3. 開発フロー（全体像）

```text
main
  ↓
spec/<Issue番号>  ……………………………… spec フェーズ（提案）
  1. Issue 起票（要望をざっくり書く）
  2. 現状仕様の参照（openwiki/ を読む）
  3. spec/<Issue番号> ブランチ作成 + OpenSpec 提案作成（Claude Code が一次作成）
  4. AI レビュー（提案）（Claude Code・Codex・qwen が指摘を並列収集 → 順番に反映、合意までループ）
  5. PR 作成（base=main, head=spec/<Issue番号>。人間によるレビューゲート、マージしない）
  6. 人間レビュー・承認
        ↓（承認後、dev/<Issue番号> を spec/<Issue番号> から分岐）
dev/<Issue番号>  ……………………………… dev フェーズ（実装）
  7. dev/<Issue番号> ブランチ作成 + 実装（Codex が一次実装）
  8. AI レビュー（コード）（Claude Code・Codex・qwen が指摘を並列収集 → 順番に反映、合意までループ）
  9. CI（typecheck / lint / clippy）
  10. ビルド確認（AI が build/<Issue番号> へ push し、実ビルドが成功するか確認。失敗したら 7 に戻って修正、成功するまでループ）
  11. PR 作成（base=main, head=build/<Issue番号>。人間による動作チェックゲート、マージしない）
  12. ユーザー動作検証・承認
  13. OpenSpec アーカイブ（`openspec-archive-change`／`/opsx:archive` で対応する change を `openspec/specs/` に反映）
        ↓（承認後、release/<version> を最新の main から分岐し、dev/<Issue番号> をそこへ merge）
release/v<version>  ……………………………… リリースフロー（[ブランチ・リリース戦略](ブランチ・リリース戦略.md) が正）
  14. 最新の main から release/v<version> を分岐し、dev/<Issue番号> を merge する
  15. package.json・src-tauri/Cargo.toml・src-tauri/tauri.conf.json のバージョンを更新する
  16. CHANGELOG.md に対応するエントリを追記する
  17. main へマージする（通常の git merge。squash はここまでの正式なマージ履歴を潰すため使わない）
  18. v<version> タグを作成して push する → このタグ push が GitHub Actions を自動起動する（既存 `ci.yml` の `publish-tauri` は既に `refs/tags/*` の push で動く条件になっているため、実装変更は不要）。ビルドが自動で走り、成果物が draft release に添付される。成果物の動作確認は 11 の dev フェーズ PR で既に済んでいるため、ここでは行わない
  19. release/v<version> ブランチを削除する
  ↓
main
```

spec フェーズの PR（5）・dev フェーズの PR（11）はいずれも **レビューゲートであり、マージはしない**。承認は「次のブランチへ進んでよい」という合図として扱う。実際に `main` へ内容が入るのは、`release/v<version>` が上記 14〜19（詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) §3.4/§4/§5/§7 を正とする）を経て `main` にマージされたときのみである。

## 4. spec フェーズ（提案）

### 4.1 Issue 起票

- 起点は GitHub Issue とする
- この段階では要望は詳細化せず、ざっくりとした要望・課題感を書けばよい
- 例: 「ローカル STT のエラーハンドリングを改善したい」「面接後レポートに◯◯の項目を追加したい」

### 4.2 現状仕様の参照（OpenWiki）

- Issue の内容に関連する現状仕様を `openwiki/` から参照する
- 起点は `openwiki/quickstart.md`。関連ページ（`architecture/`, `domain/`, `workflows/`, `integrations/`, `operations/`, `testing/`）をたどる
- OpenWiki は生成物であり、この段階では読み取り専用として扱う。内容を直接編集しない（[CLAUDE.md](../../CLAUDE.md) の既存方針どおり）
- 目的は、Issue に書かれたざっくりした要望を、既存の実装・アーキテクチャ・制約と突き合わせて具体化するための材料集めである

### 4.3 spec ブランチ作成・OpenSpec 提案作成

- `main` から `spec/<Issue番号>` を作成する
- OpenWiki で把握した現状を踏まえ、`openspec/changes/<name>/` に対応内容を詳細化する。**一次作成は Claude Code が行う**
- 通常の構成に従う: `proposal.md`（何を・なぜ）、`design.md`（設計判断、必要な場合）、`tasks.md`（作業分解）、`specs/<capability>/spec.md`（仕様差分）
- 既存のスキル `openspec-propose`（`/opsx:propose`）を使って一括生成する
- この段階で「何を実装するか」を Issue のコメントや PR ではなく OpenSpec 側に記録することで、後から仕様変更の経緯を追跡できるようにする

**change 名の命名規則（Issue との連動）**

- change 名は `issue-<Issue番号>-<内容を表す短い名前>` の kebab-case とする（例: `issue-1-improve-stt-error-handling`）
- `openspec` CLI は change 名について「文字で始まること」「アンダースコア禁止（ハイフンのみ）」を強制しており、これは `new change` 時だけでなく `status` / `instructions` / `archive` など既存 change を読むコマンド全てで同じ検証がかかる（動作確認済み）。そのため `1_task-name` のようなアンダースコア形式や数字始まりの名前は使えない
- `openspec new change "issue-<N>-<name>" --goal "Issue #<N>"` のように `--goal` にも Issue 番号を残すと、change 名からだけでなくメタデータ（`.openspec.yaml` の `goal` フィールド）からも追跡できる

### 4.4 AI レビュー（提案）

- OpenSpec 提案（proposal / design / tasks / specs 差分）について、その時点で使える全ての AI に議論させる。現時点では Claude Code・Codex・qwen(Aider) の 3 系統
- 単に各 AI が独立にレビューして指摘を出すだけでなく、互いの指摘を共有したうえで意見交換・すり合わせを行わせ、単独のレビューでは出てこないブラッシュアップを狙う
- 目的は、単一のエージェントによる提案作成では見落としがちな抜け漏れ・矛盾・設計上の懸念を、複数系統の議論を通じてブラッシュアップすることである
- 進め方（**全 AI が合意するまで、最大 3 ラウンドまでループする**）:
  - 参加する全 AI に、作成済みの change ディレクトリ（`openspec/changes/<name>/`）一式を渡し、内容の妥当性・過不足・既存仕様（`openspec/specs/`, `openwiki/`）との整合性を確認させる。**この指摘収集は並列で行う**（各 AI が同じスナップショットを同時に見て指摘だけを出す。ファイル編集はまだ行わない）
  - 各 AI の指摘を共有し、意見が分かれた点について議論・すり合わせさせる
  - 議論の結果を踏まえ、提案ファイル自体を更新する（Issue やコメントにフィードバックを残すだけで終わらせない）。**ファイル編集はコンフリクトを避けるため 1 体ずつ順番に適用する**（同時に同じブランチへ書き込ませない）
  - 更新後の提案を改めて全 AI に提示し、再度指摘・議論を行わせる
  - 全 AI が「これで問題ない」と合意するまで、上記（並列で指摘収集 → 議論 → 提案更新〔逐次適用〕→ 再提示）のサイクルを繰り返す。**上限は 3 ラウンド**
  - 全 AI の合意が得られるか 3 ラウンドに達したら、次の 4.5 PR 作成のステップへ進む（3 ラウンドで未合意の場合は、その旨を PR 説明に明記し人間の判断に委ねる）
- このステップは提案の質を上げるためのものであり、実装（5.1）を代替するものではない

### 4.5 PR 作成・人間レビュー（spec）

- `spec/<Issue番号>` の内容で PR を作成する（base=`main`, head=`spec/<Issue番号>`）
- この PR は **レビューゲートであり、マージしない**。目的は提案内容に人間が納得しているかを確認する一呼吸を置くことである
- 提案内容を変更する場合は OpenSpec の提案ファイルを更新する（Issue 本文を書き換えない）
- 承認（Approve）を「次の dev フェーズへ進んでよい」という合図として扱う。承認をどう検知して自動で `dev/<Issue番号>` を分岐させるかは §8 未決事項を参照

## 5. dev フェーズ（実装）

### 5.1 dev ブランチ作成・実装

- spec フェーズの PR（4.5）承認後、`spec/<Issue番号>` から `dev/<Issue番号>` を分岐する（`main` から取り直さない。これにより OpenSpec 提案がそのまま引き継がれる）
- 実装内容は承認済みの OpenSpec 提案（`tasks.md`）に従う。**一次実装は Codex が行う**（spec フェーズの Claude Code から交代する）
- スキル `openspec-apply-change` 相当のプロセスを Codex 向けに実行させる。既存の `issue-implement.yml` は Claude Code CLI 専用のプロンプト設計になっているため、Codex 向けの同等プロセス整備が必要（§8 未決事項）
- 実装中に提案からの逸脱が必要になった場合は、OpenSpec 側を更新してから実装を進める

### 5.2 AI レビュー（コード）

- 実装が完了した `dev/*` の差分について、その時点で使える全ての AI に議論させる。現時点では Claude Code・Codex・qwen(Aider) の 3 系統（4.4 と同じ「全員で議論する」前提）
- 目的は、実装が OpenSpec 提案（`tasks.md` や `specs/` 差分）と整合しているか、既存コードとの一貫性、バグ、簡略化の余地などを複数系統の視点でチェックし、次工程に進む前に磨き上げることである
- 進め方（**全 AI が合意するまで、最大 3 ラウンドまでループする**、4.4 と同じ並列収集・逐次適用の方式）:
  - 参加する全 AI に `dev/*` の差分を渡し、OpenSpec 提案との整合性・品質・簡潔さを確認させる。**指摘収集は並列**
  - 各 AI の指摘を共有し、意見が分かれた点について議論・すり合わせさせる
  - 議論の結果を踏まえ、実装自体を修正する。**編集は 1 体ずつ順番に適用する**
  - 修正後の差分を改めて全 AI に提示し、再度指摘・議論を行わせる
  - 全 AI が「これで問題ない」と合意するまで、上記サイクルを繰り返す。**上限は 3 ラウンド**
  - 全 AI の合意が得られるか 3 ラウンドに達したら、次の 5.3 CI へ進む（3 ラウンドで未合意の場合は、その旨を PR 説明に明記し人間の判断に委ねる）
- 人間によるコードレビューや `/code-review`（ultrareview 等）を代替するものではなく、その前段でコードの質を底上げする位置づけとする

### 5.3 CI

- `.github/workflows/ci.yml` の既存チェック（フロントエンド typecheck / lint、Rust fmt / clippy）をそのまま利用する
- Issue 駆動フローに特化した追加 CI は現時点では想定しない

### 5.4 ビルド確認

- CI（5.3）を通過した `dev/<Issue番号>` の内容を、AI が `build/<Issue番号>`（`dev/<Issue番号>` をミラーする専用ブランチ）へ push する
- `build/<Issue番号>` への push をトリガーに、実際にアプリをビルドする。`dev/*` への毎コミットでは重いビルドを走らせない（`build/<name>` を分けている理由そのもの）
- ビルドが失敗した場合は実装（5.1）に戻って修正し、AI が再度 `build/<Issue番号>` へ push する。ビルドが成功するまでこのサイクルを繰り返す
- ここではビルドが通ることの確認のみを行う。実際にアプリを動かしての検証はユーザーが行う 5.5 で扱う

### 5.5 PR 作成・ユーザー動作検証（dev）

- ビルドが成功した `build/<Issue番号>` を使い、ユーザーが成果物をダウンロードできる状態にした PR を作成する（base=`main`, head=`build/<Issue番号>`）
- PR の説明には対応する Issue 番号と OpenSpec change 名を記載し、追跡可能にする
- この PR も **レビューゲートであり、マージしない**。目的はあくまで成果物をユーザーに渡し、動作検証してもらうことである
- ユーザーは PR からビルド済み成果物をダウンロードし、実際にインストール・動作させて検証する。ソースコードは読まない
- 動作検証はユーザー本人にしかできない直列のボトルネックである。複数 Issue が並行して進んでいても、動作検証は 1 件ずつ順番に処理する
- 問題が見つかった場合は実装（5.1）に戻り、必要なら AI レビュー（コード・5.2）からやり直す
- 動作検証で問題がなければユーザーは PR を承認（Approve）する。承認は次の 5.6 OpenSpec アーカイブ以降の自動処理を進めてよいという合図として扱う（`dev/<Issue番号>` を安定ブランチへ直接マージしない点は変わらない）

### 5.6 OpenSpec アーカイブ

- 承認（5.5）の直後に、`openspec-archive-change`（`/opsx:archive`）で対応する OpenSpec change をアーカイブし、`openspec/specs/` に反映する
- このタイミングでアーカイブするのは、後回しにすると実施を忘れる可能性が高いためである
- 開発フローとしてはここまで。`build/<Issue番号>` と 5.5 で作成した PR はここで役目を終えるため削除・クローズする。以降は §3 図の 14〜19（最新の `main` から `release/v<version>` を分岐 → `dev/<Issue番号>` を merge → バージョン更新・CHANGELOG 追記 → `main` へマージ → タグ作成〔push を契機に GitHub Actions が自動ビルドし draft release に添付〕→ release ブランチ削除。動作確認は 11 の dev フェーズ PR で既に済んでいるため release フェーズでは行わない）というリリースフローへ進む。詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) §3.4/§4/§5/§7 を正とする。`dev/<Issue番号>` から直接分岐しないのは、spec/dev フェーズの間に `main` が別の release で先に進んでいる可能性があり、その場合 release ブランチは常に最新の `main` を基準にすべきだからである

## 6. 役割分担

| 場所 | 役割 | 更新タイミング |
| --- | --- | --- |
| GitHub Issue | 要望・課題のざっくりした起点 | 起票時のみ。詳細化は OpenSpec 側に移す |
| `openwiki/` | 現状の実装・仕様のスナップショット（生成物） | スケジュール実行の GitHub Actions で自動更新 |
| `spec/<Issue番号>` | OpenSpec 提案の作成・AI レビュー（Claude Code 一次作成） | 4.3 で作成、4.4 で更新。4.5 の PR 承認後は役目を終える（削除は任意） |
| `openspec/changes/<name>/` | 個別変更の詳細仕様・設計・タスク分解 | spec フェーズで作成、dev フェーズで更新。動作検証承認直後（5.6）にアーカイブする |
| `openspec/specs/` | マージ済みの現行仕様（正） | アーカイブ（5.6）時に反映 |
| `dev/<Issue番号>` | 実装・AI コードレビュー（Codex 一次実装） | 4.5 承認後に `spec/<Issue番号>` から分岐。5.1〜5.2 で更新 |
| `build/<Issue番号>` | `dev/*` の重いビルドを都度実行しないためのミラー用ブランチ | 5.4 でビルドが成功するまで push を繰り返す。5.5 の PR 承認後に削除 |
| spec PR（4.5） | 人間が提案内容を確認するレビューゲート（マージしない） | 4.5 で作成、承認で役目を終える |
| dev PR（5.5） | ユーザーがビルド済み成果物をダウンロードして動作検証・承認するための場（ソースレビューの場ではない） | 5.5 で作成、承認後 5.6 でクローズ |

## 7. GitHub Actions 化にあたっての方針（実装は別タスク）

- spec フェーズ（4.2〜4.4: OpenWiki 参照 → OpenSpec 提案作成 → AI レビュー（提案））と dev フェーズ（5.1〜5.4: 実装 → AI レビュー（コード）→ CI → ビルド確認）は、それぞれ専用のブランチ作成イベント・PR 承認イベントをトリガーに自動化する
- 汎用の `@claude` / `@codex` メンション型ワークフロー（`claude.yml` / `codex.yml`）は、Issue 上のコメントに反応させると spec/dev フェーズの正規トリガーと区別がつかず誤操作の原因になる（2026-08-04 の Issue #11 実装時に実際に発生した事故）。そのため Issue コメントでの起動は無効化し、PR コメントでの利用（レビュー指摘への応答など）に限定することを推奨する
- AI レビュー（4.4, 5.2）は参加する全 AI（現時点で Claude Code・Codex・qwen(Aider)）を呼び分けたうえで、指摘収集を並列に行う必要がある。GitHub Actions（特に自己ホストランナー）上でどう並列実行を実現するか（同時にプロセスを起動する／各 AI 用に一時ワークツリーを分ける等）は別途設計する
- dev フェーズの一次実装（5.1）を Codex に担当させる場合、既存 `issue-implement.yml` の `implement` ジョブ（Claude Code CLI 専用プロンプト）を Codex 向けに書き換える、または並行して用意する必要がある
- spec PR（4.5）・dev PR（5.5）双方について、承認イベントの検知（`pull_request_review` の `submitted`/`approved` 等）をトリガーに次フェーズ（dev ブランチ分岐 / OpenSpec アーカイブ）を自動実行する仕組みが必要
- ビルド確認（5.4）では、`build/<Issue番号>` への push をトリガーに、既存の `publish-tauri`（現在は tag push / 手動実行のみ）とは別に、動作検証用のビルドを走らせる仕組みが必要。既存 `ci.yml` の拡張、または別ワークフローとして新設するかは別途決める
- ワークフロー本体（YAML、権限スコープ、トリガー条件の具体設計）は本資料の対象外とし、別途 OpenSpec change として提案する
