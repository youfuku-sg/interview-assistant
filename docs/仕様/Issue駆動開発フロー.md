# Issue駆動開発フロー

## 1. 目的

この文書は、開発の起点をローカル VSCode 上での Claude Code 利用から GitHub 上に移し、GitHub Issue を起点として要件定義・設計・実装を進める今後の開発フローを整理するための資料である。

もう一つの目的として、このフローは「AI のみで開発を進められるか」を検証する場でもある。現時点では Claude Code と Codex の 2 つを組み込むが、これは最終形ではなく出発点である。将来的には他の AI（別ベンダーのコーディングエージェント等）も組み込み、複数の AI が互いに相談・レビューしながら開発を進められる体制を目指す。そのため本資料のフロー・命名規則・役割分担は、参加する AI の種類や数が増えても破綻しない形を意識して設計する。

現時点ではフローの設計のみを対象とし、GitHub Actions 上で Claude Code を実行するワークフロー本体（YAML・secret 設定等）の実装は別途行う。

本資料は **開発フロー**（Issue 起票 〜 PR 承認 〜 OpenSpec アーカイブ）のみを対象とする。それ以降の、次バージョンの想定・`release/v<version>` 作成・バージョン更新・GitHub Release 作成・タグ付け・安定ブランチ（main）へのマージといった **リリースフロー** は、引き続き [ブランチ・リリース戦略](ブランチ・リリース戦略.md) を正とする。両者を1つの「全体フロー」に詰め込むと肥大化するため、本資料では明確に切り分ける。

## 2. 前提

- 個人利用前提のプロジェクトであり、過度に複雑な運用は避ける（[ブランチ・リリース戦略](ブランチ・リリース戦略.md) と同様の方針）
- 既存の `openwiki/`（現状仕様の自動生成ドキュメント）と `openspec/`（変更提案・仕様差分の管理）の枠組みをそのまま活用する
- ブランチ運用・リリース手順は本資料では変更しない。実装フェーズは引き続き [ブランチ・リリース戦略](ブランチ・リリース戦略.md) に従う
- Claude Code の GitHub Actions 連携（`anthropics/claude-code-action`）を利用する前提とするが、具体的なトリガー設計・secret 管理は本資料では方針レベルに留める
- AI レビュー（4.4）は、個々の AI が独立にレビューして終わりではなく、その時点で使える全ての AI に議論させることを前提とする。現時点では Claude Code と Codex の 2 系統だが、参加 AI が増えてもこの「全員で議論する」という進め方自体は変えない
- AI レビュー（提案・4.4、コード・4.7）はいずれも 1 回の議論で終わらせず、参加する全 AI が合意するまで「提示 → 議論 → 修正 → 再提示」をループする
- ユーザーが開発フロー中に直接手を動かすのは、4.11 のビルド済み成果物の動作検証のみとする。ソースコードそのもののレビューはユーザーの作業範囲に含めない。それ以外（提案作成、AI レビュー、実装、コードレビュー、ビルド）は AI 主導で進める
- 動作検証（4.11）はユーザー本人にしかできない直列のボトルネックである。複数 Issue の 1〜9 が並行して進んでいても、動作検証は 1 件ずつ順番に処理する
- ビルド確認（4.9）は `feature/*` への毎コミットで重いビルドが走らないよう、専用の `build/<name>` ブランチへの push をトリガーに行う。`build/<name>` の詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) を参照

## 3. 開発フロー（全体像）

```text
1. Issue 起票（要望をざっくり書く）
        ↓
2. 現状仕様の参照（openwiki/ を読む）
        ↓
3. OpenSpec 提案作成（proposal / design / tasks / specs 差分）
        ↓
4. AI レビュー（提案）（使える全 AI が合意するまで議論・ブラッシュアップをループ）
        ↓
5. レビュー・合意（Issue コメント上で確認）
        ↓
6. 実装（feature ブランチ、既存のブランチ戦略に従う）
        ↓
7. AI レビュー（コード）（使える全 AI が合意するまで議論・ブラッシュアップをループ）
        ↓
8. CI（typecheck / lint / clippy）
        ↓
9. ビルド確認（AI が `build/<name>` へ push し、実ビルドが成功するか確認。失敗したら 6 に戻って修正、成功するまでループ）
        ↓
10. PR 作成（ビルド済み成果物をダウンロード可能な状態にしてユーザーへ提示）
        ↓
11. ユーザー動作検証（成果物をダウンロードして動作確認のみ行う。ソースは見ない。NG なら 6 に戻る。人間のボトルネックのため 1 件ずつ順番に処理）
        ↓
12. 承認
        ↓
13. OpenSpec アーカイブ（承認直後に実行。後回しにすると忘れるため、ここで確定させる）
        ↓
   ここから先はリリースフロー（次バージョンの想定・release ブランチ作成・バージョン更新・GitHub Release・タグ付け・main マージ）。
   詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) を参照
```

## 4. 各ステップの詳細

### 4.1 Issue 起票

- 起点は GitHub Issue とする
- この段階では要望は詳細化せず、ざっくりとした要望・課題感を書けばよい
- 例: 「ローカル STT のエラーハンドリングを改善したい」「面接後レポートに◯◯の項目を追加したい」

### 4.2 現状仕様の参照（OpenWiki）

- Issue の内容に関連する現状仕様を `openwiki/` から参照する
- 起点は `openwiki/quickstart.md`。関連ページ（`architecture/`, `domain/`, `workflows/`, `integrations/`, `operations/`, `testing/`）をたどる
- OpenWiki は生成物であり、この段階では読み取り専用として扱う。内容を直接編集しない（[CLAUDE.md](../../CLAUDE.md) の既存方針どおり）
- 目的は、Issue に書かれたざっくりした要望を、既存の実装・アーキテクチャ・制約と突き合わせて具体化するための材料集めである

### 4.3 OpenSpec 提案作成

- OpenWiki で把握した現状を踏まえ、`openspec/changes/<name>/` に対応内容を詳細化する
- 通常の構成に従う: `proposal.md`（何を・なぜ）、`design.md`（設計判断、必要な場合）、`tasks.md`（作業分解）、`specs/<capability>/spec.md`（仕様差分）
- 既存のスキル `openspec-propose`（`/opsx:propose`）を使って一括生成する
- この段階で「何を実装するか」を Issue のコメントや PR ではなく OpenSpec 側に記録することで、後から仕様変更の経緯を追跡できるようにする

**change 名の命名規則（Issue との連動）**

- change 名は `issue-<Issue番号>-<内容を表す短い名前>` の kebab-case とする（例: `issue-1-improve-stt-error-handling`）
- `openspec` CLI は change 名について「文字で始まること」「アンダースコア禁止（ハイフンのみ）」を強制しており、これは `new change` 時だけでなく `status` / `instructions` / `archive` など既存 change を読むコマンド全てで同じ検証がかかる（動作確認済み）。そのため `1_task-name` のようなアンダースコア形式や数字始まりの名前は使えない
- `openspec new change "issue-<N>-<name>" --goal "Issue #<N>"` のように `--goal` にも Issue 番号を残すと、change 名からだけでなくメタデータ（`.openspec.yaml` の `goal` フィールド）からも追跡できる

### 4.4 AI レビュー（提案）

- OpenSpec 提案（proposal / design / tasks / specs 差分）について、その時点で使える全ての AI に議論させる。現時点では Claude Code と Codex の 2 系統
- 単に各 AI が独立にレビューして指摘を出すだけでなく、互いの指摘を共有したうえで意見交換・すり合わせを行わせ、単独のレビューでは出てこないブラッシュアップを狙う
- 目的は、単一のエージェントによる提案作成では見落としがちな抜け漏れ・矛盾・設計上の懸念を、複数系統の議論を通じてブラッシュアップすることである
- Claude Code と Codex は現時点で参加する 2 系統であり、最終的な構成ではない。将来的に他の AI が加わっても、このステップに「議論の参加者を 1 系統追加する」形で拡張できることを想定する（§1・§2 参照）
- 進め方（**全 AI が合意するまでループする**）:
  - 参加する全 AI に、作成済みの change ディレクトリ（`openspec/changes/<name>/`）一式を渡し、内容の妥当性・過不足・既存仕様（`openspec/specs/`, `openwiki/`）との整合性を確認させる
  - 各 AI の指摘を共有し、意見が分かれた点について議論・すり合わせさせる
  - 議論の結果を踏まえ、提案ファイル自体を更新する（Issue やコメントにフィードバックを残すだけで終わらせない）
  - 更新後の提案を改めて全 AI に提示し、再度指摘・議論を行わせる
  - 全 AI が「これで問題ない」と合意するまで、上記（提示 → 議論 → 提案更新 → 再提示）のサイクルを繰り返す
  - 全 AI の合意が得られて初めて次の 4.5 レビュー・合意のステップへ進む
- このステップは提案の質を上げるためのものであり、実装（4.6）を代替するものではない

### 4.5 レビュー・合意

- OpenSpec 提案の内容を Issue 上（または提案自体）でレビューする
- 個人利用前提のため厳密な承認フローは設けないが、実装に進む前に内容に納得しているかを確認する一呼吸を置く
- 提案内容を変更する場合は OpenSpec の提案ファイルを更新する（Issue 本文を書き換えない）

### 4.6 実装

- 実装は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) の `feature/<name>` ブランチで行う
- 実装内容は承認済みの OpenSpec 提案（`tasks.md`）に従う。スキル `openspec-apply-change`（実装コマンド）を使う
- 実装中に提案からの逸脱が必要になった場合は、OpenSpec 側を更新してから実装を進める

### 4.7 AI レビュー（コード）

- 実装が完了した `feature/*` の差分について、その時点で使える全ての AI に議論させる。現時点では Claude Code と Codex の 2 系統（4.4 と同じ「全員で議論する」前提。§1・§2 参照）
- 目的は、実装が OpenSpec 提案（`tasks.md` や `specs/` 差分）と整合しているか、既存コードとの一貫性、バグ、簡略化の余地などを複数系統の視点でチェックし、マージ前に磨き上げることである
- 進め方（**全 AI が合意するまでループする**）:
  - 参加する全 AI に `feature/*` の差分を渡し、OpenSpec 提案との整合性・品質・簡潔さを確認させる
  - 各 AI の指摘を共有し、意見が分かれた点について議論・すり合わせさせる
  - 議論の結果を踏まえ、実装自体を修正する
  - 修正後の差分を改めて全 AI に提示し、再度指摘・議論を行わせる
  - 全 AI が「これで問題ない」と合意するまで、上記（提示 → 議論 → 実装修正 → 再提示）のサイクルを繰り返す
  - 全 AI の合意が得られて初めて次の 4.8 CI へ進む
- 人間によるコードレビューや `/code-review`（ultrareview 等）を代替するものではなく、その前段でコードの質を底上げする位置づけとする

### 4.8 CI

- `.github/workflows/ci.yml` の既存チェック（フロントエンド typecheck / lint、Rust fmt / clippy）をそのまま利用する
- Issue 駆動フローに特化した追加 CI は現時点では想定しない

### 4.9 ビルド確認

- CI（4.8）を通過した `feature/*` の内容を、AI が `build/<name>`（`feature/<name>` をミラーする専用ブランチ）へ push する
- `build/<name>` への push をトリガーに、実際にアプリをビルドする。`feature/*` への毎コミットでは重いビルドを走らせない（`build/<name>` を分けている理由そのもの）
- ビルドが失敗した場合は実装（4.6）に戻って修正し、AI が再度 `build/<name>` へ push する。ビルドが成功するまでこのサイクルを繰り返す
- ここではビルドが通ることの確認のみを行う。実際にアプリを動かしての検証はユーザーが行う 4.11 で扱う

### 4.10 PR 作成

- ビルドが成功した `build/<name>` を使い、ユーザーが成果物をダウンロードできる状態にした PR を作成する
- PR の説明には対応する Issue 番号と OpenSpec change 名を記載し、追跡可能にする
- この時点ではソースコードの差分レビューを求めるものではない。目的はあくまで成果物をユーザーに渡すことである

### 4.11 ユーザー動作検証

- ユーザーは PR からビルド済み成果物をダウンロードし、実際にインストール・動作させて検証する
- ユーザーがこのフローで直接行う作業はこれだけである。ソースコードは読まない
- 動作検証はユーザー本人にしかできない直列のボトルネックである。複数 Issue が並行して 1〜9 まで進んでいても、動作検証は 1 件ずつ順番に処理する
- 問題が見つかった場合は実装（4.6）に戻り、必要なら AI レビュー（コード・4.7）からやり直す

### 4.12 承認

- 動作検証（4.11）で問題がなければ、ユーザーは PR を承認（Approve）する
- 承認はこの PR を実際にマージするためのものではない（`feature/*` を安定ブランチへ直接マージしない、既存のブランチ戦略のルールに変わりはない）。承認は次の 4.13 以降の自動処理を進めてよいという合図として扱う

### 4.13 OpenSpec アーカイブ

- 承認（4.12）の直後に、`openspec-archive-change`（`/opsx:archive`）で対応する OpenSpec change をアーカイブし、`openspec/specs/` に反映する
- このタイミングでアーカイブするのは、後回しにすると実施を忘れる可能性が高いためである
- 開発フローとしてはここまで。`build/<name>` と 4.10 で作成した PR はここで役目を終えるため削除・クローズする。以降は `feature/<name>` から `release/v<version>` を分岐し、[ブランチ・リリース戦略](ブランチ・リリース戦略.md) のリリースフロー（次バージョンの想定・バージョン更新・GitHub Release・タグ付け・main マージ）へ進む

## 5. 役割分担

| 場所 | 役割 | 更新タイミング |
| --- | --- | --- |
| GitHub Issue | 要望・課題のざっくりした起点 | 起票時のみ。詳細化は OpenSpec 側に移す |
| `openwiki/` | 現状の実装・仕様のスナップショット（生成物） | スケジュール実行の GitHub Actions で自動更新 |
| `openspec/changes/<name>/` | 個別変更の詳細仕様・設計・タスク分解 | 提案時に作成、実装中に更新。PR 承認直後（4.13）にアーカイブする |
| `openspec/specs/` | マージ済みの現行仕様（正） | アーカイブ（4.13）時に反映 |
| `build/<name>` | `feature/*` の重いビルドを都度実行しないためのミラー用ブランチ | 4.9 でビルドが成功するまで push を繰り返す。承認（4.12）後に削除 |
| Pull Request | ユーザーがビルド済み成果物をダウンロードして動作検証・承認するための場（本資料が扱うのはこの検証用 PR。ソースレビューの場ではない） | 4.10 で作成、4.11〜4.12 で使用、4.13 でクローズ |

## 6. GitHub Actions 化にあたっての方針（実装は別タスク）

- Issue 上の `@claude` メンション等をトリガーに、上記 4.2〜4.4（OpenWiki 参照 → OpenSpec 提案作成 → AI レビュー（提案））を自動化する想定
- AI レビュー（4.4, 4.7）は参加する全 AI（現時点で Claude Code と Codex）を呼び分けたうえで議論させる必要があるため、GitHub Actions 上で一部の AI しか動かせない場合の代替手段（動かせない AI はローカル実行のまま残す等）も検討する
- 実装フェーズ（4.6）を自動化するか、人間がローカル/VSCodeで引き続き行うかは別途決める
- 実装後の AI レビュー（4.7）を PR 作成前（feature ブランチ上）で行うか、PR 作成後にワークフローとして自動起動するかは別途決める
- 導入には `anthropics/claude-code-action` の GitHub App 導入と `ANTHROPIC_API_KEY` の secret 登録が必要。Codex 側を GitHub Actions 上で動かす場合は別途 Codex 用の認証・実行手段の調査が必要
- ビルド確認（4.9）では、`build/<name>` への push をトリガーに、既存の `publish-tauri`（現在は tag push / 手動実行のみ）とは別に、動作検証用のビルドを走らせる仕組みが必要。既存 `ci.yml` の拡張、または別ワークフローとして新設するかは別途決める
- 承認（4.12）イベントの検知（`pull_request_review` の `submitted`/`approved` 等）をトリガーに、OpenSpec アーカイブ（4.13）を自動実行する仕組みが必要
- ワークフロー本体（YAML、権限スコープ、トリガー条件の具体設計）は本資料の対象外とし、別途 OpenSpec change として提案する

## 7. 未決事項

- Issue 上での提案作成を Claude Code (GitHub Actions) に自動でやらせるか、当面は手動で行うか
- AI レビュー（4.4, 4.7）を GitHub Actions 上で自動化するか、当面は手動で各 AI をそれぞれ起動するか
- 複数 AI に議論させる際の具体的な進行方法（順番にレビューを回すのか、同じ場に指摘を集約して同時に見せるのか等）。提案レビュー（4.4）とコードレビュー（4.7）で進行方法を変えるかどうかも含む
- コードに対する AI レビュー（4.7）と、既存の `/code-review`（ultrareview 等、人間が起動する多エージェントレビュー）との役割分担・重複範囲
- AI レビューの指摘・議論の経緯を、提案ファイルへの直接反映以外にどこかへ記録として残すか（例: change ディレクトリ内に議事録的なファイルを残す等）
- ビルド確認（4.9）でのビルド成果物をどう配布するか（GitHub Actions の artifact、draft release への添付など）と、対象 OS の範囲（Windows のみか、リリースフローと同様 macOS/Linux も含めるか）
- ビルド確認（4.9）ごとにビルドすると、`release/v<version>` でのリリース用ビルドと二重にビルドすることになるが、それを許容するか、何らかの形で共通化するか
- 実装フェーズ（4.6）まで GitHub Actions に任せるか、実装は引き続きローカルの VSCode / Claude Code で行うか
- Claude Code / Codex 以外の AI をどのタイミング・どういう形で組み込むか（4.4 のレビュアー追加か、提案作成や実装自体を任せるか）
- 複数 AI が意見を出した際の最終判断者（人間が引き続き最終判断するか、AI 同士の合議で決めるか）
- OpenSpec 提案作成を自動化する場合のトリガー条件（Issue ラベル、`@claude` メンション等）
- AI レビュー（4.4, 4.7）のループに上限回数を設けるか（合意に至らず長期化・無限ループする場合の歯止め）
- ユーザー動作検証（4.11）が複数 Issue で同時に「検証待ち」になった場合の待ち行列をどう表現するか（Issue ラベル、GitHub Projects のステータス列等）
