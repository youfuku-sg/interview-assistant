# Issue駆動開発フロー

## 1. 目的

この文書は、開発の起点をローカル VSCode 上での Claude Code 利用から GitHub 上に移し、GitHub Issue を起点として要件定義・設計・実装を進める今後の開発フローを整理するための資料である。

もう一つの目的として、このフローは「AI のみで開発を進められるか」を検証する場でもある。現時点では Claude Code と Codex の 2 つを組み込むが、これは最終形ではなく出発点である。将来的には他の AI（別ベンダーのコーディングエージェント等）も組み込み、複数の AI が互いに相談・レビューしながら開発を進められる体制を目指す。そのため本資料のフロー・命名規則・役割分担は、参加する AI の種類や数が増えても破綻しない形を意識して設計する。

本資料は **開発フロー**（Issue 起票 〜 dev フェーズ PR 承認 〜 OpenSpec アーカイブ）のみを対象とする。それ以降の、次バージョンの想定・`release/v<version>` 作成・バージョン更新・GitHub Release 作成・タグ付け・安定ブランチ（main）へのマージといった **リリースフロー** は、引き続き [ブランチ・リリース戦略](ブランチ・リリース戦略.md) を正とする。両者を1つの「全体フロー」に詰め込むと肥大化するため、本資料では明確に切り分ける。

## 2. 前提

- 個人利用前提のプロジェクトであり、過度に複雑な運用は避ける（[ブランチ・リリース戦略](ブランチ・リリース戦略.md) と同様の方針）
- 既存の `openwiki/`（現状仕様の自動生成ドキュメント）と `openspec/`（変更提案・仕様差分の管理）の枠組みをそのまま活用する
- 開発フローは **spec フェーズ**（提案）と **dev フェーズ**（実装）の 2 段階に明確に分離する（§3）。それぞれ専用ブランチ（`spec/<Issue番号>` / `dev/<Issue番号>`）を持ち、各フェーズの終わりに人間が確認する PR を置く。フェーズの切り替えをコメントコマンド（`@claude` 等の呼び分け）に頼らず、ブランチ構造そのもので表現することで、「どのトリガーを使えばよいか」が曖昧にならないようにする
- `dev/<Issue番号>` は `spec/<Issue番号>` から分岐する（`main` から取り直さない）。これにより spec フェーズで作成した OpenSpec 提案が dev フェーズにそのまま引き継がれる
- ブランチ運用・リリース手順は本資料では変更しない。`release/v<version>` 以降は引き続き [ブランチ・リリース戦略](ブランチ・リリース戦略.md) に従う
- 各フェーズの一次作成者を固定する: **spec フェーズは Claude Code が一次作成**、**dev フェーズは Codex が一次実装**を担当する。これはフェーズごとに異なる AI に主体性を持たせるための役割分担である
- **AI 同士が指摘を出し合い、合意が取れるまで議論・修正をループする自動レビュー工程（旧 §4.4「AI レビュー（提案）」・旧 §5.2「AI レビュー（コード）」）は廃止した。** Issue #16 の実運用で承認ゲート検知の自動化不備・並列レビュー→再トリガーのワークフローバグに直面し、その反省を踏まえて設計した後継案（`feature/<Issue番号>` 単一パイプライン、未マージ）でも実運用（TEST〜TEST8、8 回中成功 1 回）で機構自体が安定して機能しなかったため。提案・実装の品質担保は、各フェーズ末尾の人間レビュー PR（§4.4, §5.4）と通常の CI（§5.2）に委ねる
- ユーザーが開発フロー中に直接手を動かすのは、各フェーズ末尾の PR レビュー（spec フェーズ: 提案内容の確認、dev フェーズ: ビルド済み成果物の動作検証）のみとする。ソースコードそのもののレビューはユーザーの作業範囲に含めない。それ以外（提案作成、実装、CI、ビルド）は AI 主導で進める
- dev フェーズの動作検証（5.4 相当）はユーザー本人にしかできない直列のボトルネックである。複数 Issue の spec/dev フェーズが並行して進んでいても、動作検証は 1 件ずつ順番に処理する
- ビルド確認（§3 の 7）は、`feature/<Issue番号>` に対して `build.yml` を `workflow_dispatch` で直接実行する。専用の `build/<name>` ミラーブランチは使わない（2026-08-22 に廃止。実ビルドの頻度が上がる代わりに、ブランチ・PR の構成をシンプルに保つ判断）
- Claude Code・Codex を呼び出すステップ（OpenSpec 提案作成・実装など）は、GitHub-hosted runner ではなく自己ホストランナー（Windows）上で実行する。Claude Code・Codex はサブスクリプション契約の CLI ログインで使っており、その Windows 機にインストール・認証済みの CLI をそのまま利用したいため。API トークン課金（`CLAUDE_CODE_OAUTH_TOKEN` / `CODEX_AUTH_JSON` 等を GitHub Secrets に置く方式）は当面保留とする（自己ホストでうまくいかない場合はこちらへの切り替えを再検討する）。一方、AI を使わない部分（release フェーズ＝§3 の 11〜17、既存の `publish-tauri` によるビルド等）は引き続き GitHub-hosted runner でよい
- `feature/<Issue番号>` は `develop`（`main` からではなく）から分岐する。`develop` には `.claude`/`.codex`/`openspec`/`openwiki`/`docs`/`AGENTS.md`/`CLAUDE.md` など AI 開発ツール関連のファイル一式を含める。`main` はこれらを含まない、リリース済みの最小構成を保つ（[ブランチ・リリース戦略](ブランチ・リリース戦略.md) §3.1 参照）。dev PR（§3 の 8）も base=`develop` とする

## 3. 開発フロー（全体像）

```text
develop
  ↓
  1. Issue 起票（要望をざっくり書く。ユーザーが書く）
        ↓
feature/<Issue番号>  ……………………………… 提案 + 実装（単一ブランチで連続実行）
  2. OpenWiki を最新化する（`openwiki-update.yml` を実行し、現状仕様のスナップショットを最新化する）
  3. 現状仕様の参照（openwiki/ を読む）
  4. feature/<Issue番号> ブランチ作成 + OpenSpec 提案作成（Claude Code が一次作成）
  5. 実装（Codex が一次実装）
  6. CI（typecheck / lint / clippy）
  7. ビルド確認（AI が `build.yml` を feature/<Issue番号> に対して `workflow_dispatch` で実行し、実ビルドが成功するか確認。失敗したら 5 に戻って修正、成功するまでループ）
  8. PR 作成（base=develop, head=feature/<Issue番号>。人間による唯一のゲート＝動作チェック後に develop へマージする）
  9. ユーザー動作検証 → 問題なければ PR を develop へマージ
  10. OpenSpec アーカイブ（9 のマージをトリガーに自動実行。`openspec-archive-change`／`/opsx:archive` で対応する change を `openspec/specs/` に反映）
        ↓（アーカイブ後、release/<version> を最新の main から分岐し、feature/<Issue番号> をそこへ merge）
release/v<version>  ……………………………… リリースフロー（[ブランチ・リリース戦略](ブランチ・リリース戦略.md) が正）
  11. 最新の main から release/v<version> を分岐し、feature/<Issue番号> を merge する
  12. package.json・src-tauri/Cargo.toml・src-tauri/tauri.conf.json のバージョンを更新する
  13. CHANGELOG.md に対応するエントリを追記する
  14. AI 開発ツール関連のファイル（`.claude`, `.codex`, `openspec`, `AGENTS.md`, `CLAUDE.md`, `docs`, `openwiki`）を release ブランチ上で取り除く（`.github/workflows/`・`CHANGELOG.md` は対象外）
  15. main へマージする（通常の git merge。squash はここまでの正式なマージ履歴を潰すため使わない）
  16. v<version> タグを作成して push する → このタグ push が GitHub Actions を自動起動する（既存 `ci.yml` の `publish-tauri` は既に `refs/tags/*` の push で動く条件になっているため、実装変更は不要）。ビルドが自動で走り、成果物が draft release に添付される。成果物の動作確認は 8 の PR で既に済んでいるため、ここでは行わない
  17. release/v<version> ブランチを削除する
  ↓
main
```

人間が直接手を動かすのは、**8〜9 の PR レビュー（動作検証・マージ）1 箇所のみ**である。Issue 起票（1）を除けば、OpenWiki 更新（2）から提案（4）・実装・CI・ビルド確認（5〜7）までは人間の承認を待たず自動で連続実行する。PR（8）は develop 向けの通常の PR であり、動作検証（9）ができたらユーザー自身がこの PR を `develop` へマージする。**このマージが「次のステップ（OpenSpec アーカイブ・リリースフロー）へ進んでよい」という合図**であり、`archive-on-approval` ジョブはこのマージイベント（`pull_request: closed, merged==true`）をトリガーに起動する（承認レビューではなくマージそのものをトリガーにしているのは、Issue #30 で「承認ではなくマージした」ことにより自動アーカイブが起動しなかった問題を踏まえた設計）。実際に `main` へ内容が入るのは、`release/v<version>` が上記 11〜17（詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) §3.4/§4/§5/§7 を正とする）を経て `main` にマージされたときのみであり、`develop` 自体は `main` へ直接マージされない。

## 4. spec フェーズ（提案）

### 4.1 Issue 起票

- 起点は GitHub Issue とする
- この段階では要望は詳細化せず、ざっくりとした要望・課題感を書けばよい
- 例: 「ローカル STT のエラーハンドリングを改善したい」「面接後レポートに◯◯の項目を追加したい」

### 4.2 現状仕様の参照（OpenWiki）

- Issue の内容に関連する現状仕様を `openwiki/` から参照する
- 起点は `openwiki/quickstart.md`。関連ページ（`architecture/`, `domain/`, `workflows/`, `integrations/`, `operations/`, `testing/`）をたどる
- OpenWiki は生成物であり、この段階では読み取り専用として扱う。内容を直接編集しない（[CLAUDE.md](../../CLAUDE.md) の既存方針どおり）
- 目的は、Issue に書かれたざっくりした要望を、既存の実装・アーキテクチャ・制約と突き合わせて具体化するための材料集めである

### 4.3 spec ブランチ作成・OpenSpec 提案作成

- `main` から `spec/<Issue番号>` を作成する
- OpenWiki で把握した現状を踏まえ、`openspec/changes/<name>/` に対応内容を詳細化する。**一次作成は Claude Code が行う**
- 通常の構成に従う: `proposal.md`（何を・なぜ）、`design.md`（設計判断、必要な場合）、`tasks.md`（作業分解）、`specs/<capability>/spec.md`（仕様差分）
- 既存のスキル `openspec-propose`（`/opsx:propose`）を使って一括生成する
- この段階で「何を実装するか」を Issue のコメントや PR ではなく OpenSpec 側に記録することで、後から仕様変更の経緯を追跡できるようにする

**change 名の命名規則（Issue との連動）**

- change 名は `issue-<Issue番号>-<内容を表す短い名前>` の kebab-case とする（例: `issue-1-improve-stt-error-handling`）
- `openspec` CLI は change 名について「文字で始まること」「アンダースコア禁止（ハイフンのみ）」を強制しており、これは `new change` 時だけでなく `status` / `instructions` / `archive` など既存 change を読むコマンド全てで同じ検証がかかる（動作確認済み）。そのため `1_task-name` のようなアンダースコア形式や数字始まりの名前は使えない
- `openspec new change "issue-<N>-<name>" --goal "Issue #<N>"` のように `--goal` にも Issue 番号を残すと、change 名からだけでなくメタデータ（`.openspec.yaml` の `goal` フィールド）からも追跡できる

### 4.4 PR 作成・人間レビュー（spec）

- `spec/<Issue番号>` の内容で PR を作成する（base=`main`, head=`spec/<Issue番号>`）
- この PR は **レビューゲートであり、マージしない**。目的は提案内容に人間が納得しているかを確認する一呼吸を置くことである
- 提案内容を変更する場合は OpenSpec の提案ファイルを更新する（Issue 本文を書き換えない）
- 承認（Approve）を「次の dev フェーズへ進んでよい」という合図として扱う。承認をどう検知して自動で `dev/<Issue番号>` を分岐させるかは §8 未決事項を参照

## 5. dev フェーズ（実装）

### 5.1 dev ブランチ作成・実装

- spec フェーズの PR（4.4）承認後、`spec/<Issue番号>` から `dev/<Issue番号>` を分岐する（`main` から取り直さない。これにより OpenSpec 提案がそのまま引き継がれる）
- 実装内容は承認済みの OpenSpec 提案（`tasks.md`）に従う。**一次実装は Codex が行う**（spec フェーズの Claude Code から交代する）
- スキル `openspec-apply-change` 相当のプロセスを Codex 向けに実行させる。既存の `issue-implement.yml` は Claude Code CLI 専用のプロンプト設計になっているため、Codex 向けの同等プロセス整備が必要（§8 未決事項）
- 実装中に提案からの逸脱が必要になった場合は、OpenSpec 側を更新してから実装を進める

### 5.2 CI

- `.github/workflows/ci.yml` の既存チェック（フロントエンド typecheck / lint、Rust fmt / clippy）をそのまま利用する
- Issue 駆動フローに特化した追加 CI は現時点では想定しない

### 5.3 ビルド確認

- CI（5.2）を通過した `dev/<Issue番号>` の内容を、AI が `build/<Issue番号>`（`dev/<Issue番号>` をミラーする専用ブランチ）へ push する
- `build/<Issue番号>` への push をトリガーに、実際にアプリをビルドする。`dev/*` への毎コミットでは重いビルドを走らせない（`build/<name>` を分けている理由そのもの）
- ビルドが失敗した場合は実装（5.1）に戻って修正し、AI が再度 `build/<Issue番号>` へ push する。ビルドが成功するまでこのサイクルを繰り返す
- ここではビルドが通ることの確認のみを行う。実際にアプリを動かしての検証はユーザーが行う 5.4 で扱う

### 5.4 PR 作成・ユーザー動作検証（dev）

- ビルドが成功した `build/<Issue番号>` を使い、ユーザーが成果物をダウンロードできる状態にした PR を作成する（base=`main`, head=`build/<Issue番号>`）
- PR の説明には対応する Issue 番号と OpenSpec change 名を記載し、追跡可能にする
- この PR も **レビューゲートであり、マージしない**。目的はあくまで成果物をユーザーに渡し、動作検証してもらうことである
- ユーザーは PR からビルド済み成果物をダウンロードし、実際にインストール・動作させて検証する。ソースコードは読まない
- 動作検証はユーザー本人にしかできない直列のボトルネックである。複数 Issue が並行して進んでいても、動作検証は 1 件ずつ順番に処理する
- 問題が見つかった場合は実装（5.1）に戻り、修正後は再度ビルド確認（5.3）を経てから PR をやり直す
- 動作検証で問題がなければユーザーは PR を承認（Approve）する。承認は次の 5.5 OpenSpec アーカイブ以降の自動処理を進めてよいという合図として扱う（`dev/<Issue番号>` を安定ブランチへ直接マージしない点は変わらない）

### 5.5 OpenSpec アーカイブ

- 承認（5.4）の直後に、`openspec-archive-change`（`/opsx:archive`）で対応する OpenSpec change をアーカイブし、`openspec/specs/` に反映する
- このタイミングでアーカイブするのは、後回しにすると実施を忘れる可能性が高いためである
- 開発フローとしてはここまで。`build/<Issue番号>` と 5.4 で作成した PR はここで役目を終えるため削除・クローズする。以降は §3 図の 12〜17（最新の `main` から `release/v<version>` を分岐 → `dev/<Issue番号>` を merge → バージョン更新・CHANGELOG 追記 → `main` へマージ → タグ作成〔push を契機に GitHub Actions が自動ビルドし draft release に添付〕→ release ブランチ削除。動作確認は 9 の dev フェーズ PR で既に済んでいるため release フェーズでは行わない）というリリースフローへ進む。詳細は [ブランチ・リリース戦略](ブランチ・リリース戦略.md) §3.4/§4/§5/§7 を正とする。`dev/<Issue番号>` から直接分岐しないのは、spec/dev フェーズの間に `main` が別の release で先に進んでいる可能性があり、その場合 release ブランチは常に最新の `main` を基準にすべきだからである

## 6. 役割分担

| 場所 | 役割 | 更新タイミング |
| --- | --- | --- |
| GitHub Issue | 要望・課題のざっくりした起点 | 起票時のみ。詳細化は OpenSpec 側に移す |
| `openwiki/` | 現状の実装・仕様のスナップショット（生成物） | スケジュール実行の GitHub Actions で自動更新 |
| `spec/<Issue番号>` | OpenSpec 提案の作成（Claude Code 一次作成） | 4.3 で作成。4.4 の PR 承認後は役目を終える（削除は任意） |
| `openspec/changes/<name>/` | 個別変更の詳細仕様・設計・タスク分解 | spec フェーズで作成、dev フェーズで更新。動作検証承認直後（5.5）にアーカイブする |
| `openspec/specs/` | マージ済みの現行仕様（正） | アーカイブ（5.5）時に反映 |
| `dev/<Issue番号>` | 実装（Codex 一次実装） | 4.4 承認後に `spec/<Issue番号>` から分岐。5.1 で更新 |
| `build/<Issue番号>` | `dev/*` の重いビルドを都度実行しないためのミラー用ブランチ | 5.3 でビルドが成功するまで push を繰り返す。5.4 の PR 承認後に削除 |
| spec PR（4.4） | 人間が提案内容を確認するレビューゲート（マージしない） | 4.4 で作成、承認で役目を終える |
| dev PR（5.4） | ユーザーがビルド済み成果物をダウンロードして動作検証・承認するための場（ソースレビューの場ではない） | 5.4 で作成、承認後 5.5 でクローズ |

## 7. GitHub Actions 化にあたっての方針（実装は別タスク）

- spec フェーズ（4.2〜4.3: OpenWiki 参照 → OpenSpec 提案作成）と dev フェーズ（5.1〜5.3: 実装 → CI → ビルド確認）は、それぞれ専用のブランチ作成イベント・PR 承認イベントをトリガーに自動化する
- 汎用の `@claude` / `@codex` メンション型ワークフロー（`claude.yml` / `codex.yml`）は、Issue 上のコメントに反応させると spec/dev フェーズの正規トリガーと区別がつかず誤操作の原因になる（2026-08-04 の Issue #11 実装時に実際に発生した事故）。そのため Issue コメントでの起動は無効化し、PR コメントでの利用（レビュー指摘への応答など）に限定することを推奨する
- dev フェーズの一次実装（5.1）を Codex に担当させる場合、既存 `issue-implement.yml` の `implement` ジョブ（Claude Code CLI 専用プロンプト）を Codex 向けに書き換える、または並行して用意する必要がある
- spec PR（4.4）・dev PR（5.4）双方について、承認イベントの検知（`pull_request_review` の `submitted`/`approved` 等）をトリガーに次フェーズ（dev ブランチ分岐 / OpenSpec アーカイブ）を自動実行する仕組みが必要
- ビルド確認（5.3）では、`build/<Issue番号>` への push をトリガーに、既存の `publish-tauri`（現在は tag push / 手動実行のみ）とは別に、動作検証用のビルドを走らせる仕組みが必要。既存 `ci.yml` の拡張、または別ワークフローとして新設するかは別途決める
