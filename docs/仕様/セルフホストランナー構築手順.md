# セルフホストランナー構築手順

## 1. 目的

この文書は、GitHub Actions のジョブを自分の Windows PC 上で実行する「セルフホストランナー」の構築手順を整理するための資料である。

対象読者は将来の自分（別プロジェクトで同じセットアップを再利用するとき）を含む。そのため、Interview-Assistant 固有の内容はできるだけ含めず、汎用的な手順として書く。**新しいリポジトリが完成し次第、そちらへ移す前提**であり、この文書自体は暫定的にこのリポジトリの `docs/仕様/` に置いている。

## 2. 背景・前提

GitHub 提供のホスト型ランナー（`ubuntu-latest` / `windows-latest` 等）では届かない、次のようなローカル資源を GitHub Actions のワークフローから使いたい場合にセルフホストランナーが必要になる。

- Windows PC 上で動いているローカル LLM（例: Ollama、LM Studio 等。`localhost` 経由でしか到達できない）
- その PC に既にログイン・認証済みの Claude Code（`claude` CLI）
- その PC に既にログイン・認証済みの Codex（`codex` CLI）

これらはホスト型ランナー（毎回使い捨ての別マシン）からは原則アクセスできないため、実際にその PC 上でジョブを実行するセルフホストランナーが必要になる。

前提:

- 対象は個人の Windows PC 1 台
- 複数プロジェクト（複数リポジトリ）で同じランナーを使い回したい

## 3. 登録スコープの選択

セルフホストランナーは以下のいずれかのスコープに登録する。1つのランナーインスタンスは同時に1つのスコープにしか属せない（リポジトリ登録のランナーを後から Organization 登録に変えることは可能だが、一度登録解除して登録し直す必要がある）。

| スコープ | 特徴 |
| --- | --- |
| リポジトリ単位 | そのリポジトリ専用。複数リポジトリで使い回すには、リポジトリごとに別のランナーインスタンス（フォルダ・サービス）を用意する必要がある |
| Organization 単位 | Organization 配下の複数リポジトリから共有できる。個人アカウントでは利用できず、Organization（無料プランでも可）の作成が必要 |

複数プロジェクトでの再利用が目的のため、**Organization 単位での登録を推奨**する。個人アカウントしか持っていない場合は、先に（無料でよいので）GitHub Organization を作成する。

Organization の Default runner group はどのプランでも利用できる。追加の runner group 作成など高度な権限管理を行う場合は GitHub Team プラン以上が必要になるが、素朴に「1つのランナーを複数リポジトリで共有する」だけであれば Default group で足りる。

## 4. 導入手順

### 4.1 Organization の準備（未作成の場合）

1. GitHub で新規 Organization を作成する（無料プランで可）
2. 対象リポジトリ（Interview-Assistant を含む、今後使い回したいリポジトリ）をその Organization に移すか、Organization 内で新規作成する
   - 既存の個人リポジトリを Organization 配下に移す場合は Transfer 機能を使う（別途検討）

### 4.2 ランナーの登録

1. Organization の **Settings → Actions → Runners → New runner** を開く
2. OS に `Windows`、アーキテクチャに `x64` を選択する
3. 画面に表示される PowerShell コマンドをそのまま Windows PC 上で実行する。おおよそ次の形になる（トークンは画面に表示されたものを使う。有効期限があるため都度取得する）:

```powershell
mkdir actions-runner; cd actions-runner
Invoke-WebRequest -Uri <画面に表示された runner zip の URL> -OutFile actions-runner-win-x64.zip
Expand-Archive -Path actions-runner-win-x64.zip -DestinationPath $PWD
./config.cmd --url https://github.com/<organization> --token <画面に表示されたトークン>
```

4. `config.cmd` の対話プロンプトで以下を設定する
   - ランナーグループ: 特に理由がなければ Default
   - ランナー名: PC を識別できる名前（例: `home-windows-pc`）
   - **ラベル**: 用途を識別できるラベルを追加する（例: `windows`, `local-llm`, `local-ai-cli`）。ワークフロー側の `runs-on` でこのラベルを指定して呼び分ける

### 4.3 常駐化（Windows サービス化）

対話実行（`./run.cmd`）のままだとターミナルを閉じると止まってしまうため、Windows サービスとして常駐させる。

```powershell
./svc.cmd install
./svc.cmd start
```

**重要**: デフォルトではサービスのログオンアカウントが `NT AUTHORITY\NETWORK SERVICE` 等になり、対話ユーザーのログイン情報（`claude` / `codex` の認証情報、ローカル LLM への到達性）を参照できない可能性がある。

サービスのログオンアカウントを、実際に `claude` / `codex` にログイン済みのユーザーアカウントに変更する:

1. Windows の「サービス」管理画面（`services.msc`）を開く
2. 該当するランナーサービス（`actions.runner.<org>.<runner名>` のような名前）を探す
3. プロパティ → 「ログオン」タブ → 「このアカウント」を選択し、対話ログインで使っているユーザーアカウントとパスワードを設定する
4. サービスを再起動する

### 4.4 動作確認

適当なテスト用ワークフロー（`runs-on: [self-hosted, windows, local-llm]` のようにラベル指定したもの）を実行し、ジョブがそのランナーで実行されること、および `claude` / `codex` コマンドやローカル LLM の API（`http://localhost:<port>/...`）にジョブから到達できることを確認する。

## 5. ワークフロー側での参照方法

セルフホストランナーを使うジョブは、ホスト型ランナー名の代わりにラベルの配列を指定する。

```yaml
jobs:
  example:
    runs-on: [self-hosted, windows, local-llm]
```

## 6. Claude Code / Codex CLI の認証再利用

### 6.1 Claude Code

- 推奨: `claude setup-token` をそのPC上で実行して Claude Code の OAuth トークンを発行し、Organization/リポジトリの secret（例: `CLAUDE_CODE_OAUTH_TOKEN`）として登録する。`anthropics/claude-code-action` は `claude_code_oauth_token` 入力でこれを直接受け付ける（API キー課金を避け、Pro/Max 等の契約をそのまま使える）
- あるいは、マーケットプレイスの Action を経由せず、ワークフローのステップで直接 `claude` コマンドを呼び出す方法もある。この場合はサービスのログオンアカウントがログイン済みユーザーと一致している必要がある（4.3 参照）

### 6.2 Codex

- `openai/codex-action` は現時点で API キー入力（`openai-api-key`）のみに対応しており、ChatGPT プラン（サブスクリプション）ログインには対応していない
- そのため、ChatGPT プランのログインをそのまま使いたい場合は **Action を経由せず、ワークフローのステップで直接 `codex exec` を呼び出す**
- Codex CLI はログイン情報を `~/.codex/auth.json` に保持し、アクセストークンを自動リフレッシュする。常駐するセルフホストランナー（4.3 でログオンアカウントを合わせたもの）であれば、この仕組みがそのまま機能し、追加の secret 管理は不要
- 参考: OpenAI の CI/CD 向けドキュメントでは、ephemeral な（都度使い捨ての）ランナーの場合は `auth.json` を secret に退避・復元する運用が案内されているが、常駐セルフホストランナーではその手間が不要になる

## 7. ローカル LLM へのアクセス

ローカル LLM サーバー（Ollama や LM Studio 等）が同じ PC 上の `localhost` で待ち受けていれば、セルフホストランナーのジョブからは通常のネットワークアクセスと同様に到達できる。ホスト型ランナーでは原理的に不可能だった部分であり、これがセルフホストランナーを導入する主目的の一つである。

## 8. セキュリティ上の注意点

- セルフホストランナーはホスト型ランナーと異なり、**サンドボックス化されず、実行するマシンそのものに対してジョブが直接アクセスできる**。ワークフローの内容を信頼できる場合のみ使うこと
- Organization / リポジトリを private のまま維持し、書き込み権限を持つのは本人のみにする
- 秘密情報（API キー、`claude`/`codex` の認証情報など）がジョブのログに出力されないよう、ワークフロー作成時に注意する

## 9. 未決事項

- Organization 名、リポジトリの Organization への移行タイミング
- ランナーのラベル命名規則（プロジェクトをまたいで一貫した命名にするか）
- 複数プロジェクトのジョブが同時に同じランナーへ来た場合の扱い（セルフホストランナーは基本的に1ジョブずつ直列実行されるため、詰まった場合の対処）
- Windows PC のスリープ・シャットダウンとランナー常駐の両立（PC の電源管理設定の見直しが必要になる可能性）
- 本文書を新しいリポジトリへ移す具体的なタイミングと方法
