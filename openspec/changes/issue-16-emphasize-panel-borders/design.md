## Context

`src/pages/app/index.tsx` の右エリアは3段固定レイアウトで、上段・中段の下端に `border-b border-border/40` が設定されている（下段は最後の段のため境界線なし）。`border-border` はテーマ変数 `--border`（`src/global.css`）を参照する共通デザイントークンで、ライトモードでは `oklch(0.922 0 0)`（不透明な薄灰色）、ダークモードでは `oklch(1 0 0 / 10%)`（白 10%不透明度）と定義されている。現状のクラス指定はこのトークンにさらに Tailwind の `/40`（40%不透明度）修飾を重ねているため、実効コントラストはライトモードで「背景白に対し 0.922 明度 × 40%」、ダークモードでは「10%不透明度 × 40% ≒ 4%不透明度」まで減衰し、特にダークモードでほぼ視認できない状態になっている。Issue #16 はこの境界線が分かりづらい点の改善を求めている。

## Goals / Non-Goals

**Goals:**
- 上段・中段の境界線を、ライト・ダーク両テーマで明確に視認できる強調度に引き上げる。
- 既存のデザイントークン（`--border` 等）の体系を崩さず、コンポーネント個別のハードコードされた色を極力避ける。

**Non-Goals:**
- 下段への境界線追加（下段は元々「最後の段」として境界線を持たない設計であり、今回のIssueも上段・中段間の見づらさを指摘しているため対象外とする）。
- 3段構造そのものやパネルの役割（文字起こし／要約／AI回答）の実際の変更（挙動を変えることは行わない）。ただし、`openspec/specs/top-bar-ui/spec.md` 側の記述が既存実装（後述）と食い違っている箇所は、境界線シナリオと合わせてspecのテキストを実態に合わせて修正する。これはspecの誤りの是正であり、動作変更ではない。
- ダークモード/ライトモード切り替えロジックの変更。

## Decisions

- **不透明度修飾 `/40` を撤廃し、トークンの標準不透明度（`border-border`）をそのまま使う**。理由: `/40` によるさらなる減衰が視認性低下の主因であり、これを外すだけでライトモードは2.5倍、ダークモードは10倍の不透明度になる。`--border` はアプリ全体で使われる共通境界線トークンであり、これをそのまま使うことでカード等、他の境界線表現との一貫性も保てる。
- **境界線の太さを `border-b`（1px）から `border-b-2`（2px）に変更する**。理由: ダークモードの `--border` はトークン自体が `10%` 不透明度と低めに設計されており、不透明度修飾を外すだけでは依然として控えめな見え方に留まる可能性がある。色をハードコードで濃くするとテーマ体系から外れるため、代わりに太さを1段階上げることで、テーマ設計（トークンの色・不透明度）を尊重したまま視覚的な強調度を上げる。
  - 検討した代替案: (a) `--border` トークン自体の値を変更する — グローバルな影響範囲が大きく（カード、入力欄など他の境界線すべてに波及する）、Issue #16 の対象範囲を超えるため見送り。(b) 個別に濃い色（例: `border-muted-foreground/60`）をハードコードする — テーマ切り替え時の一貫性が失われ、他の境界線表現と乖離するため見送り。
- **上段・中段の2箇所のみ変更し、下段は変更しない**。理由: 下段はそもそも境界線を持たない設計（最後の段のため）であり、Issue の指摘対象は「段の境界線」であって下段の下端ではない。
- **`openspec/specs/top-bar-ui/spec.md`「Top bar right panel layout」要件のうち、境界線以外の陳腐化した記述（中段=AI回答パネル、下段=テキスト入力欄、上段・中段が高さ半分ずつ）もこの変更で修正する**。理由: 実装（`src/pages/app/index.tsx`）は既に別変更 `top-bar-transcript-summary-panel` の実装タスク（1〜3）により中段=要約パネル・下段=AI回答パネル・3段均等・テキスト入力欄非表示となっているが、同変更はspec同期・アーカイブ（tasks.md 4.3以降の動作確認）が未完了のままメインspecに反映されていない。本提案がこの陳腐化したrequirementブロックを変更対象にする以上、境界線シナリオだけを直しても他のシナリオが実態と矛盾したまま残ってしまう。`top-bar-transcript-summary-panel` 側のspec同期を待って作業をブロックするより、その変更が既にdelta specとして用意していた正しい記述（`openspec/changes/top-bar-transcript-summary-panel/specs/top-bar-ui/spec.md`）を踏襲してこの提案内で反映する方が、spec全体の整合性を早く回復できる。挙動自体は変更しない（既存実装のテキスト化のみ）。

## Risks / Trade-offs

- [`border-b-2` により各段の実効表示高さがわずかに減る（1px→2px、2箇所で計2px程度）] → 3段はいずれも `flex-1` で残り高さを均等分配しているため、2px程度の減少はコンテンツの表示に実質的な影響を与えないと判断する。
- [視覚的な強調度の「十分さ」は主観評価に依存する] → 実装後、ユーザー自身による dev フェーズの動作検証（ライト・ダーク両テーマ）で最終確認する。

## Migration Plan

- 単一ブランチでの実装・動作確認後、既存のリリースフローに従って `main` へ反映する。CSS/Tailwindクラスの変更のみでデータ・状態・API に影響しないため、データマイグレーションやロールバック時の特別な考慮は不要（直前コミットに戻すのみで復元可能）。
